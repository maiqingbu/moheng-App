# ADR-033 — Model Calls Do Not Hold the Project Writer

状态：PROPOSED（待项目负责人评审）

关联：ADR-032（写入者有界等待）、FX-15、NFR-REC（恢复）、NFR-COST（预算先于传输）

## 背景

ADR-032 规定：写入者被占用时，其他写请求最多等待 3 秒，超时返回 `PROJECT_BUSY`。这一规则默认“写入者只会被短暂占用”。实际情况并非如此：

1. `DurableModelRunner::execute`（`repositories/runtime.rs`）在**同一个写连接上**依次完成：幂等检查与预算校验 → 持久化 `RUNNING` → `transport.send`（网络请求，可能数十秒）→ 持久化原始回复与实际用量 → 解析。
2. 调用方在整个流程期间都持有写入权：
   - 章节生产 `run_chapter_production_inner`（`production.rs`）一开始就 `manager.open`，持有写入权直到整章结束，其间包括规划、写作、审核、修复等多次模型调用，通常持续数分钟；
   - B14 完结助手 `query_b14_skill_runtime`（`commands.rs`）同样全程持有写入权。
3. 结果：生产或助手运行期间，用户的任何保存都会在等待 3 秒后得到“项目正在处理后台任务”。

现有设计中已经具备崩溃安全的基础：发送前 `RUNNING` 已经落库；重启后遇到 `RUNNING` 会转为 `UNKNOWN_REMOTE_OUTCOME`，等待用户明确处理，不会自动重发，因此也不会重复扣费。

## 决定

**原则：写入权只用于短暂的数据库阶段；任何网络 I/O 期间都不持有写入权。**

### 1. 模型调用拆成三段

| 阶段 | 是否持有写入权 | 内容 |
|---|---|---|
| A 登记 | 是（短暂） | 幂等检查、预算校验与占用、持久化 `RUNNING`；提交后释放 |
| B 发送 | **否** | `transport.send`，不接触数据库连接 |
| C 落库 | 是（短暂，按 ADR-032 有界等待） | 持久化原始回复、结算用量、解析结果 |

- `ModelTransport` 中需要数据库连接的钩子（`before_send`、`before_raw_persist`、`usage_after_raw_persist`）分别归入 A、C 阶段执行。
- `DurableModelRunner` 提供分阶段 API；现有 `execute(connection, …)` 保留给仍在同一阶段内调用的场景，直到全部调用方迁移完成后再移除。

### 2. 阶段 C 取不到写入权时：先落本地文件，再落库

付费拿到的回复不能丢，也不应长时间只放在内存里（负责人原则：数据尽量走本地存储）。

- 阶段 C 按 ADR-032 申请写入权；若返回 `PROJECT_BUSY`，先把原始回复写入项目目录下的本地暂存文件 `pending-model-responses/<model_run_id>.json`（写入后 fsync），然后按退避策略重试落库。
- 落库成功后删除暂存文件。
- 重启恢复时：若 `model_runs` 为 `RUNNING` 且存在对应暂存文件，**先导入暂存回复**，再走现有流程；没有暂存文件时，仍转为 `UNKNOWN_REMOTE_OUTCOME`（不变）。

### 3. 调用方的写入权范围

- **章节生产**：拆成“读取上下文（读连接）→ 模型调用（三段式）→ 正式提交（短暂写入权）”。正式提交沿用现有保护：`expectedProjectRevision` 校验，以及 FX-8.4 起首次提交也执行的最终审核重验。生产期间用户如果改动了相关事实，提交会被拦截并给出原因，不会静默覆盖。
- 作业进度（`jobs` 表状态、检查点）每次只短暂持有写入权。
- **B14 完结助手**：读取用读连接，模型调用用三段式；它没有正式写入，只有模型运行记录。

### 4. 并发规则

- 同一项目可以同时有多个在途模型调用；每个调用由 `model_run_id` 唯一标识，阶段 A、C 都是幂等的。
- 预算在阶段 A 占用（按预估成本），在阶段 C 按实际用量结算；并发调用不会绕过预算上限。
- 正式写入仍然只经 `CommitService + CommitBundle V2`，规则不变。

## 不在本 ADR 范围

- 不修改迁移文件、表结构或任何 `*_FROZEN.md`；暂存文件属于项目目录下的运行时文件，随项目备份与删除。
- 不改变 `UNKNOWN_REMOTE_OUTCOME` 的人工处理流程。

## 需要的测试（FX-15 实施时）

1. 模型发送期间，另一线程的写命令在 3 秒内成功（当前会得到 `PROJECT_BUSY`）。
2. 阶段 C 写入权被占用：回复落入暂存文件；释放后自动落库并删除暂存文件；费用只结算一次。
3. 阶段 A 之后、阶段 C 之前进程崩溃：有暂存文件 → 重启导入并完成；没有暂存文件 → `UNKNOWN_REMOTE_OUTCOME`，不自动重发。
4. 章节生产期间用户修改了冲突事实 → 正式提交被拦截，回执说明原因，无部分写入。
5. 并发两次模型调用都不越过预算上限。
6. 既有 B08、B12、B14、FX-10 测试全部通过；ADR-032 的同线程重入规则不变。

## 影响与代价

- 用户在生产或助手运行期间可以正常保存。
- 生产流程需要按阶段重组，这是本批工作量的主体，涉及 `production.rs` 中约 1000 行流程代码。
- 正式提交时因并发修改而被拦截的情况会变多（以前是被写锁挡在外面），这类拦截需要在界面上给出清楚的说明和“重新准备本章”的入口。
