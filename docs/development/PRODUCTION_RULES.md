# 墨衡生产与验收规则

2026 年 11 月 24 日，规则草案。本文供章纲、写作、审计、终审和验收共同使用，也规定今后新增生产环节的完成条件。本次制定规范，运行时接线和验收迁移须逐项验证。

## 1. 一套规则贯穿生产

- **规则只有一个来源。** 延用现有 JSON 输出规范的做法，从同一份版本化规则组装模型输入、执行校验和生成验收条件。各阶段可以有不同任务和提示措辞，适用规则、状态含义和完成条件必须一致。业务规则写在规则合同里，提示词只负责告诉模型如何完成本阶段任务。
- **同一章使用同一组依据。** 生产开始时固定规则版本、正式方向、卷纲、章纲、前文事实及证据的版本。写手、审计与终审均引用这组依据。提交前复查依据是否仍有效。规则或上游证据已变化时，找到受影响的阶段重新检查，已有且仍有效的正文与证据可复用。
- **正文、事实和核验状态分开记录。** 正式正文说明读者看到了什么。事实与事件记录说明系统确认了什么。任务状态说明预定结果完成到哪一步。上章已经写出的动作，在取证失败后仍是接续的前提。系统可以复核它，也可以要求本章推进后果。
- **模型提供候选，业务代码判定能否采用。** JSON 结构、身份、版本、前置条件、证据归属、状态转移和重复提交由代码检查。模型可以判断文意、选取原文、提出结论。缺乏足够证据的语义结论进入待核实状态。模型给出的「完成」「通过」或硬伤标签均须经过相应校验。
- **每条规则指明何时生效。** 登记规则时写明适用入口、所需证据、负责判定的模块和失败处理。口头禅、描写频率等编辑问题沿用提醒和局部改写。已确证的关键重演与状态倒退按第 5 节处理。改变放行、暂停或通过条件时，须更新规则版本及对应验收用例。
- **沿用现有权威数据。** 正式事实、事件、任务、正文与回执继续由现有所有者管理。跨阶段传递引用和快照。新增字段应进入对应合同，避免为同一事实建立另一份可独立修改的账本。

## 2. 写之前固定小步和章节目标

用户已确认，**全书方向通过复核并有可执行的小步后，才开始卷一**。系统先核对签约和当前正式卷纲，再为本章发出可执行的要求。写手依照已批准的章纲兑现本章结果，并在作品允许的范围内选择篇幅、语气和场景表现。

每个必做小步至少明确以下信息。后续实现优先扩展现有卷纲、章纲和证据合同。

| 信息 | 执行要求 |
| --- | --- |
| 任务与目标 | 用当前卷纲的任务 ID 定位。把描述中的必要动作、对象、条件与预定后果拆成可单独验收的要求。一个句子中的多个结果分别检查。 |
| 前文已经发生的事 | 引用当前正式原文、已确认事件或状态，以及完成情况。近期未核验的尝试也列明出处，供比对正文。 |
| 本章必须发生的变化 | 指定人物知道了什么、做成了什么、失去了什么，或关系、风险、限制如何变化。撤回、复发、再次尝试须能说明新的触发原因和后果。 |
| 本章可选内容 | 允许环境描写、缓冲、回顾与伏笔。这类内容可以服务叙事，有独立新后果时按证据核对。 |
| 证据与结案 | 每项必要条件需要能支持它的证据。缺项逐项列出。全部满足且前置任务有效后，才将小步标为完成。 |

例如第 62 轮的目标是「比对松脂纽扣背面的四道刻痕与蚀骨粉纹路，确认二者同源」。取得纽扣、比对竹筒内壁、比对蚀骨粉、证实同源分别记录。旧章若只写过筒壁比对，下一章从这个结果继续找粉末证据。若旧章实际已经证实同源，先对原正式版本复核，并在实际发生的那一章补录证据。

## 3. 四个环节按同一标准交接

| 环节 | 必须读取 | 必须交付 | 谁有权改变结果 |
| --- | --- | --- | --- |
| 章纲 | 规则版本、获批方向、当前小步、已发生结果、未覆盖条件 | 本章角色、所承接的状态、预定新增结果、必做条件 | 章纲可以提出安排。修改已批准的目标或事实，走现有调整入口。 |
| 写手 | 同一章纲和事实依据，相关前文章段 | 正文实际写出的动作与后果。关键道具来源、持有变化或时间跳转须能从正文读出。 | 写手可以改变表现形式。要改变必做结果时，提交章纲变更。 |
| 审计 | 同一目标、前文事实、定版前的候选正文 | 逐项记录本章新增结果、可定位的原文、未满足条件和待核实项 | 审计可提取候选事实。核验通过后由现有提交入口入库。 |
| 终审 | 同一目标及版本、审计证据、当前正文和相关前文 | 对有争议的事项给出确证、排除或待核实的依据，指出对应条件和前后证据 | 提交入口按同一规则核验结论并决定放行或暂停。作者保留处理被暂停草稿及批准剧情变更的权力。 |

任何后置环节发现前置要求有误，须把具体问题交回拥有该要求的环节。汇报时区分原要求、发现的问题和处理记录，后续阶段仍使用已生效版本。

## 4. 用原文证明结果

1. **先核原文归属。** 模型优先返回输入中的章节和句子编号，程序从指定版本正文取实际引文。入库凭据绑定作品、章节、正式版本、散列、引用范围和对应条件。单字短句可以定位上下文，上下文须能证明结论。拼接或省略后的引文须补证后才能使用。
2. **再核做好了什么。** 对照对象、动作、必要条件和结果，逐项找能支持结论的原文。取得物品可证明持有变化，完成指定比对需要对应的结果证据。推测、意图、提问和听来的说法分别记录其语气或知情范围。关键词、同义词或字面重合只用于寻找值得检查的段落。
3. **判断结果何时发生。** 对比此前正式事件、正文和已验证成果。此前已经发生的证据可用于补核当时的小步。对旧发现的回顾可以保留，本章进展应落在明确的新后果上。再次行动须核对新的尝试、对象、条件或结果，明确改变了什么。
4. **核对是否真的矛盾。** 状态倒退须指向同一实体的同一部位或属性，核实故事顺序以及正文是否交代变化。小指第一节仍有裂口和第二节白点退去可以同时成立。怀疑人物说谎或认错对象时，先区分其认知与作品事实。
5. **只保留已核验的部分。** 候选证据逐段核对。有一段写得过长或无法定位时，其他独立、有效的证据仍可采用。已验证的部分成果与缺项同时保存。已发布的源章被换版时，基于旧版的结果须复核，已结案的小步按现有规则重算。

## 5. 失败、暂停和重试都有明确出口

| 情况 | 系统处理 |
| --- | --- |
| JSON 形状错误或证据编号无法定位 | 优先修正规范字段和引用。按版本约定限次补证，复用已有正文与有效证据，记录拒绝的字段及原因。 |
| 本章确无某项新结果，或暂时无法证实 | 小步保持待办或部分完成，正面记录已经核实的部分。按现有入库规则处理其他成果。样章验收仍列出缺项，下一章从正文已发生的动作继续。 |
| 自动改写后仍有前后原文确证的关键重演或状态倒退（持续状态的再次描写只留提醒，不暂停；2026-11-25 负责人决定） | 保留草稿并暂停续写，由作者决定怎么处理。这是已确认的产品规则。显示前后证据、涉及的结果，以及已尝试的改写。 |
| 复核意见分歧，证据不足 | 保留待复核记录，明确缺哪段证据或哪项结论需要确认。复核人员可据同一版本原文裁定。 |
| 预算、服务或未知远端结果 | 按现有运行时规则停在相应边界。未知远端结果等待显式决定。规划和写作开始前为必要的审计、取证与最终复核预留预算。可选润色在额度紧张时让位。 |

同一错误在重试后仍存在时，留下最后一次原因及下一步所需材料。成功的步骤继续按其有效版本复用。更换模型、规则、目标或上下文后重新验证，报告说明是哪项变化。

## 6. 验收分别记录三项结论

1. **流程完成。** 相应命令是否执行，章回执是否正式提交，进度能否从数据库重开后回读。
2. **证据通过。** 章纲约定的必做结果是否逐项有证据，来源、引用和运行记录是否绑定当前版本。没有完成的小步继续待办。
3. **正文质量通过。** 人工编辑复核是否确认新事件、新后果和状态承接成立。自动核对齐全时，样章仍须填写正文复核结论。整体通过需要三项都满足。脚本和界面分别展示三项，流程成功的退出码只表示执行完成。

十章试点继续沿用已选定的每章推进证据口径。开跑前记录章号范围、必做结果、连续性条件和回查要求，整轮都按当时的口径判定。正式生产安排缓冲章时，先明确该章角色和要兑现的叙事作用，再对照同一份验收标准。

付费验收前先固定并回放既有样章，让同一输入可以跨版本比较。

| 归档案例 | 待拦截或待区分 | 对照应通过 |
| --- | --- | --- |
| 第 33 轮 | 车辙再偏半尺、坛水状态倒退 | 有原因的新偏移，正文交代过的水位变化 |
| 第 50、52 轮 | 换措辞重演结果，对话或线索被误记为完成 | 已知发现带来新推断或决策 |
| 第 58 轮 | 银灰仍在原处被判断为再次掉落 | 原状态延续，另一粒银灰产生可核对的新后果 |
| 第 59 轮 | 同一批材料冒充不同批，预算先用完 | 不同批次确有证据，关键校验仍有额度 |
| 第 62 轮 | 拿到纽扣冒充同源比对、不同指节的状态被判冲突、长引文导致整份回包失效 | 对象别称已有交代的真比对、可同时成立的不同部位状态、同一回包中的有效短引文 |

回放须绑定正文、模型回包、规则版本和裁决理由。检查程序能否识别旧错误，也检查正常场景会不会误停。上述改造涉及的反例和工程回归通过后，再进行一次受控真模链路验证。

## 7. 今后的每项开发怎样算完成

进入实现前，先把功能说明写成下面这张清单。一个改动牵涉多个环节时，各负责人共用同一份清单。

| 必须写清 | 可以复查的结果 |
| --- | --- |
| 需求、入口与完成条件 | 指定谁从哪里发起、会看到什么结果、哪些情况属于失败。明确本次范围和规则版本。 |
| 所有者与上下游 | 指定哪个模块有权写状态、哪些地方读取它、模型何时只提出候选。列出输入、输出和证据版本。 |
| 失败路径与恢复 | 列出超时、重复提交、并发改版、旧版本兼容和部分执行。写明保留什么、从哪里继续、何时需要人工决定。 |
| 回归与实际证据 | 用固定输入建立反例和正常对照。再走真实入口验证落库、回执和重开读回。外部模型行为需要独立验证时才使用真模。 |
| 收尾 | 回读每项完成条件。能核实的写成结论，待验证的写明证据缺口。新需求与技术欠账单列，原任务按原定范围验收。 |

这套流程的第一项实现以第 62 轮的“同源比对”为切片。先冻结案例和预期判定，再把共享的小步要求接入章纲、写手、审计及终审。通过反例与正向对照后，再推广到其他卷和后续任务。

## 现有代码对应位置

- 第一批接线使用 `stage-step.r1`。章纲保存系统从正式方向、卷纲、当前小步及现有证据生成的规则摘要。生产继续前和提交前复查摘要。审计记录使用的条件、是否取到新结果，以及支持结果的动作引文和结果引文。
- 第 63 轮取证回放补充 `stage-step.r2`。同一条件的动作和后果可以出现在本章两处。各自引用一至三句，分别保存正文范围，并核对先后顺序。该版本使用存档做离线回归。
- `stage-step.r3` 允许在续写审计中补核同一小步的正式原章。先前保留为待核验的章节中，最早一次和最近两次可送审。模型指定来源章节，程序复查正式版本并分别绑定动作与结果。阶段进度按成果实际发生的章节登记，补核回执记录验证所在章。只有当前章自己的证据才计入当前章的新增推进。替换原章后，失效证据撤回，受影响的小步按剩余证据重新开启。
- 续跑沿用可读的草稿检查点。终审需要核对已检查正文的散列及引用版本。之前因额度或错误未完成终审时，恢复所需额度后重新检查草稿，并复核仍适用的旧疑点。额度仍不足时保留待复核状态。
- 开篇签约的 F1-5 由生产和签约共用同一个计数实现。开篇正文按连续 12 个字符计数，同一个片段在一个章节内或跨章节累计出现三次即超限。ASCII 字母、ASCII 数字及连字符合计至少占一半的片段沿用签约豁免。起稿可以收到一次更正反馈，补写候选引入超限片段时保留底稿。审计前查验本章和已提交的开篇，正式提交时再读当前前文查验。旧的审计检查点仍含超限片段时按草稿继续修整。
- 同批补写的每段内容应独立承接它的原文位置。如果其中一段引入了连续百字复制，程序可以丢弃该段，仍按原定位采纳通过重复检查的其他段。后续连续性复核和审计使用实际采纳后的全章。
- 前章计划中的目标、人物、地点和用法用于回看写作安排。新章起始状态引用已发布的事实、事件和正文。计划中预写的结尾、结果和钩子不随计划记录送入下一章提示。
- `chapter-goal.r1` 在原有主事件检查中另外核对正式章纲的目标。系统分别绑定章纲版本、正文散列和证据。主事件与章纲兑现各留结论，人物确有新发现时可以登记，未展示的计划结果仍需复核。模型语义判断仍需正文复核。
- 审计发现的新伏笔由系统分配编号。推进已有伏笔须指向计划或提供给审计的正式线索。缺少引用的推进单独留提醒，其余有证据的事实继续核对和入库。
- 十章验收分别报告样本是否齐全、已入库章节的证据和连续性待复核项。终审提醒与已确证的暂停有不同状态。未解除的提醒仍需证据处理，验收口径全部满足后才进入编辑复核。
- 旧章纲与旧证据仍按原有合同读取。新版规则在新编译的章纲上生效。运行时核对条件编号、原文范围和前文原句，并对比对类目标检查结果证据。不同措辞下的等义判断仍由审读模型提供，验收保留正文复核。
