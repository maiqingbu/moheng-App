# 账本降级与模型输出规范（LD-1）

状态：负责人已批准方向（2026-10-25）。本文写清要改什么、怎么验证；按第 1～4 步依次实施，每步单独提交。

## 0. 为什么要改

2026-10-25 连续 5 轮十章真实验收失败，其中 4 轮卡在“记账”而不是正文质量：

| 轮次 | 卡点 | 性质 |
|---|---|---|
| 1 | 第 8 章计划被退回 9 次（预告条数与写作检查来回打架） | 计划检查 |
| 2 | 签约评估 JSON 括号配错 | 输出格式 |
| 3 | 审计给线索起名 `thread-1`，不合规 | 编号 |
| 4 | 第 2 章审计又用 `thread-1`，撞上第 1 章 | 编号 |
| 5 | 签约引文差一两个字；开篇威胁不够紧迫 | 引文核对 + 真实质量 |

根因有两个：

1. **模型输出没有规范。** `contracts/` 只管系统内部数据；每个模型步骤“该输出什么”只写在提示词的英文说明里，程序检查另写在别处，两边由不同批次各自增补，逐渐不一致。
2. **检查几乎全部是“错一点整章作废”**，而且很多检查针对的是模型天生会出偏差的细节（编号、引文一字不差）。检查越多，卡点越多。

## 1. 负责人决定

| 编号 | 决定 |
|---|---|
| LD-1.1 | 每个模型步骤一份输出规范；请求（结构化输出）和检查用同一份。 |
| LD-1.2 | 编号全部由系统分配，模型不再起编号；引用已有对象只能用系统在输入里给出的编号。 |
| LD-1.3 | 引文由系统在正文里定位；差一两个字时对到最接近的原句并记录，不判“无法验证”。 |
| LD-1.4 | 只保留少数整章作废的硬检查；其余账本检查改为“提交并记录”，问题进入待处理。 |
| LD-1.5 | 字数按平台：番茄/七猫目标 2000，起点/纵横/晋江目标 3000，区间为目标的 90%～110%（行业惯例，非平台硬规定）。 |
| LD-1.6 | 平台规则（起点、晋江不接受模型正文）属于外部事实，不改判。 |

## 2. 第 1 步：模型输出规范

### 2.1 规范放在哪

- 新目录 `contracts/model-output/`，每个模型步骤一个 JSON Schema（Draft 2020-12），例如 `audit-extract.schema.json`、`signing-evaluation.schema.json`。
- 不放进 `contracts/schemas/`：那里的文件会被合同生成器处理，生成器归另一会话维护。
- Rust 侧用 `include_str!` 读入，`jsonschema` 校验（项目已依赖）。

### 2.2 一份规范，三处使用

1. **提示词**：规范原文附在系统提示末尾（`The reply must be valid against this JSON Schema: …`）。各步骤提示词里手写的形状说明在该步骤改造时删去，只留语义说明。
2. **请求格式**：阿里云一律 `json_object`。严格模式（`json_schema` + `strict`）只有 Qwen3.7/3.8 系列支持，当前用的 qwen-plus、DeepSeek 都不支持，暂不启用；换模型时再接。
3. **检查**：模型回复先按规范校验；不合规范 → 带着校验错误（`outputFeedback`）重新生成一次；第二次仍不合 → 该步骤失败（这是“格式”硬检查，见 3.1）。规范只写后续代码真正依赖的字段，不增加新的拦截。

签约评估沿用 S35 技能包自带的 outputSchema 作为它的规范。

只检查新收到的回复；续跑时复用的已存回复（重放、reusable render/audit）按当时接受的结果使用，不再检查，以免续跑因规范更新而失败。

重试会叠加（每次都单独记账、单独预留费用，不重复计费）：审计最坏 4 次（原始、规范重发、auditFeedback 重跑、再规范重发）；计划最坏 6 次（3 轮重计划 × 每轮可能一次规范重发）。每章 16 次模型调用的上限仍然兜底。

已覆盖（第 1a 步）：RENDER_CHAPTER_CRAFT、ADJUST_CHAPTER_LENGTH（`chapter-body`）、REWRITE_PASSAGES、AUDIT_EXTRACT。

### 2.3 编号由系统分配（LD-1.2）

| 对象 | 现在 | 改后 |
|---|---|---|
| 新事实 | 模型给 `factId` | 模型不给；系统分配 `canon:{章摘要}:{n}` |
| 新认知 | 模型给 `knowledgeId`，用 `factId` 指向事实 | 模型不给编号；用本次回复里事实的**序号**指向（`factIndex`） |
| 新线索 | 模型给 `threadRef` | 模型不给；系统分配 `thread:{章摘要}:{n}` |
| 推进已有线索 | 模型给 `threadRef` | 只能从输入列出的已有线索编号里选（规范里列为枚举） |
| 人物/实体 | 模型给 `subjectId` | 只能从输入列出的实体编号里选 |

`fresh_audit_ids`、`scope_bare_thread_refs` 和 FX-17 的 `new_thread:` 改名已删除，统一由 `assign_audit_ids` 处理（第 1b 步）。补充约定：

- 认知指向已提交的事实时仍用该事实的 `factId`（来自 authorityContext）。
- 模型给新事实起的名字保留为 `modelLabel`：计划任务的 `CANON_FACT_MATCH` 按系统编号或这个名字匹配；被丢弃的候选记录里也带上它。
- 序号（`factIndex`、`sourceFactIndex`）只用一次，用后即删；之后按编号追踪，丢弃部分候选再分配时不会错位。
- 同一回复里同名的新线索合并为一条。
- 已提交的章节不会再次生产（`B08_CHAPTER_ALREADY_COMMITTED`），系统编号不会覆盖旧事实。

### 2.4 引文由系统定位（LD-1.3）

模型给出引文文字；系统用 `locate_quote_span` 按顺序定位：一字不差且唯一 → 去空白后唯一 → 省略号两端 → 漏字（已有规则）→ **近似**（第 1c 步）：改动（换、加、删字）不超过引文字数的十分之一（所以引文至少 10 个字），全文没有同样接近的另一处（20 字以上的引文，差一处改动也算同样接近）；起点被改动时对齐到句读边界。命中后用原文替换引文，模型原话记在 `suppliedQuote`；都找不到 → 该条证据“未定位”（审计中丢弃该条并记录；第 2 步后进入提醒）。

签约评估同样适用（含省略号、漏字两条旧规则）：先在三章里找一字不差的，找不到再宽松定位；在标注章节或唯一另一章找到即视为已核对，原话记在 `suppliedQuote`。审计证据的原话保存在审计记录（ReviewReport）里。正文“局部重写”的定位仍只认一字不差，避免改错段落。

### 2.5 验证

用 2026-10-25 五轮真实出错的模型输出做测试夹具（审计 `thread-1`、签约括号、引文“他/沈砚”“攥着/攥紧”），全部能被正确处理。

## 3. 第 2 步：账本降级

### 3.1 保留的硬检查（会作废本章）

| 硬检查 | 说明 |
|---|---|
| 正文存在且可读 | 空正文、截断、乱码 |
| 字数在平台区间内 | 见第 4 节；超出时先“调篇幅”一次 |
| 违禁内容 | 签约 C0-2 同口径 |
| 输出格式 | 二次生成后仍不合规范 |
| 系统前提 | 章节不存在、顺序不对、预算/模型未配置、写入冲突等（非模型产出，不在本次降级范围） |

### 3.2 降级为提醒（提交章节，问题进待处理）

审计产出的每一条（事实、认知、线索、任务进度、预留揭示、证据）逐条检查；**不合格的那一条不入账**，写入提醒；其余照常入账，章节照常提交。涉及：

- 事实语义未解析（谓词、时间、范围、极性、等价）、与已有事实冲突；
- 认知时间/可见性不完整、与未来事件矛盾；
- 线索推进不在计划内、推进方式不合法、来源事件无效；
- 任务完成判定不满足、任务越界；
- 预留揭示越界；
- 证据未定位、绑定不一致、审计完整性不一致。

计划阶段的检查（地点重复、目标重复、预告条数等）同理：重计划 2 次后仍有问题 → 用最后一版计划继续写，问题写入提醒，不再让作业失败。

### 3.3 提醒长什么样

- 存为 `decisions` 表的一条记录：`decision_type = AUDIT_REMINDER`，`outcome = OPEN`，`payload.category = "审计提醒"`，含章节、原因（中文）、相关原文。
- 待处理页显示；动作“知道了”（关闭）和“去阅读页查看”。
- 一章的同类问题合并成一条，避免刷屏。

### 3.3a 实现（第 2a 步，审计部分）

- 审计检查拆成“准备”（分配编号、规范化、去掉编造的任务/预留）和“校验”（`validate_audit_completeness` + `validate_actual_extraction`）。原有的反馈重跑保留；最终仍不通过时，`hold_back_audit_items` 从空账本开始，按事实 → 认知 → 线索 → 任务 → 预留的顺序逐条加入，能通过校验的保留，不能的记入 `normalization.heldBack`（字段、条目、原因码）。
- 模型自报“有内容没整理完”（UNRESOLVED_HARD / INCOMPLETE / TRUNCATED 标签）也按“已完成”收下现有内容，并记一条提醒。
- 格式问题仍是硬检查：缺整类字段（规范不符，重发一次后仍不符）、回复截断不是 JSON。
- 2026-10-24 的决定“审计报告了事实而章节提交时一个都没有，则不提交”被 LD-1.4 取代：现在照常提交，提醒里列出全部被拦下的事实。
- 提醒：`decision_type = AUDIT_REMINDER`，一章一条，标题“第 N 章有 K 条内容没有记入作品档案”，摘要逐条写明“事实「原文」：原因”；动作“知道了”（`decision_submit` + `ACKNOWLEDGE`，只关闭仍打开的提醒，否则 `AUDIT_REMINDER_NOT_OPEN`）和“去资料页阅读本章”。
- 被拦下的条目目前只记录在提醒里；以后如需“补录”，另行设计。

### 3.4 验证

今天 5 轮里每个卡点场景各一个测试：章节提交成功，并且留下对应提醒。
