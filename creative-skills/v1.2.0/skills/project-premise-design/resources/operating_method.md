# 项目命题与核心卖点设计：运行方法 v1.1

> 来源类型：`project_method`。这是本次验收为补足/校正 Skill 可执行性加入的方法，不声称来自用户缺失的原始资料。

## 决策顺序
1. 先把命题压缩为“谁，在什么持续压力下，为了什么可重复目标，必须不断做什么高代价选择”；若只能描述世界设定而不能描述选择链，判定为没有故事发动机。
2. 核心卖点必须能在正文中被反复体验，而不是只存在于简介；至少说明它如何产生冲突、回报或认知反转。
3. 差异化优先改造“组合关系、限制条件、代价、视角或兑现方式”，不要只靠陌生名词换皮。
4. 为长期连载给出至少三条彼此不同的扩展向量：能力/资源、关系/势力、谜团/世界或身份/价值观；每条都要能产生新选择而非只扩地图。
5. 用反事实测试：去掉核心机制或核心卖点后故事是否仍几乎一样；若是，卖点没有进入因果链。
6. 风险标记至少检查：卖点一次性耗尽、主角无主动目标、世界观先于故事、平台读者承诺不匹配、扩展只能数值膨胀。

## 使用来源证据时
- `principles.md` 与 `decision_rules.md` 中的 WWC 资料仅作证据/启发；必须先检查语义是否真的对应当前输出字段。
- 禁止“因为某段被检索到，就机械绑定到某个 payload 字段”。
- 数字、平台经验、案例遵循 `../../contracts/METHOD_PRECEDENCE.md`。

## 最终检查
- 不得生成完整 BookPlan
- 不得把市场证据写成 Canon
- 至少给出 3 个长期扩展向量但保持非权威
- 任何 HARD/Canon/Knowledge 冲突优先于文学质量建议。
- 不得读取未来不该暴露给当前 POV/Renderer 的信息。
- 不得把 Skill 自身知识当成项目事实。
- 结论必须说明关键假设与不确定性。
- 能局部修复时不扩大到更高层级；确需升级则给 `nextSkillHints`。
